# Codex 账号池服务（二开分支）

本分支将 codex2api 作为 New API 的后端账号管理与请求执行服务。New API 负责用户、对外分发和计费；此服务负责原生 Codex 凭据、指纹、上游连接、账号调度和执行日志。

## 保留范围

- 原生 Codex 账号导入、Token 刷新、配额查询、启停、健康度、并发、冷却与恢复。
- HTTP 和上游 WebSocket 连接、代理、连接复用、请求取消及流式执行。
- 设备与会话指纹收敛、账号请求头覆盖、客户端版本配置及同步。
- Responses 上下文连续性、compact、工具调用、推理内容及图片输入。
- 渠道密钥鉴权、请求日志、基础用量和健康检查。
- `/admin/` 后台：账号池、调度状态、代理出口、请求日志、渠道密钥和运行设置。

账号池只加载原生 Codex 凭据。数据库保留旧渠道记录与迁移结构以兼容已有数据；它们不会进入 Codex 调度池。已裁剪的审核配置在服务模式中不生效。

单账号管理入口和显式 ID 的批量操作也校验渠道。批次包含旧的非 Codex 账号时，整个请求在执行前拒绝，避免更改这些保留记录。账号列表使用服务端分页与搜索。

## 已退出服务范围

其他渠道的管理入口、生图/视频、Realtime、Gemini 原生入口、公开门户、Prompt 审核管理、质量测试及随机客户端遥测发送已移除。

原后台的仪表盘分析、回收站管理、订阅升级与每日结算视图、账号分组管理、综合运维报表等入口不再注册。凭据导入/OAuth、订阅有效期查询、调度并发、模型冷却、账号模型配置和代理绑定入口仍保留。

## 后台配置与账号信息

运行设置和账号配置均提供中文帮助。枚举选项显示中文含义、当前选择说明和可展开的全部取值解释；只保存实际编辑的字段。

- “新账号默认收敛模式”用于未明确指定模式的新账号，不批量修改已有账号。`device` 统一设备标识，`session` 进一步统一会话，`full` 再统一线程；`single_machine_multi_window` 共享设备但保留真实窗口及子线程的身份关系。已有账号在“账号配置”页调整。
- “独立代理 URL”可从已配置代理中选择，也可手动填写；列表显示标签、脱敏地址及禁用/异常提示，加载失败不清空已有绑定。选择“继承默认出口”并保存才清空账号覆盖。导入账号时也可选择代理。
- “账号时区”可选择中文常用时区或浏览器支持的其他 IANA 时区，也可手动填写。已有自定义时区会保留；选择“保留下游时区”并保存才清空覆盖。此项影响上游请求的环境时区，不改变后台页面时间显示。
- 普通表单中的暂停阈值使用百分数，例如 `95` 表示 95%；接口和高级 JSON 仍使用 `0.95`。账号阈值留空或 0 继承分组/全局值；要取消此账号的阈值暂停，使用对应的独立开关。上游真实额度限制仍然有效。
- 列表使用后端的 `usage_percent_5h` / `usage_percent_7d` 字段显示已用比例；未知额度显示“未获取”，不当作 0%。长周期按上游元数据区分 7 天与月周期。
- “额度与有效期”页区分额度重置时间、订阅到期、Access Token 到期、凭据最近刷新及配额最近刷新。未返回的时间显示“—”，不表示永不过期。页面时间按浏览器时区显示。
- “刷新额度”查询上游快照；“刷新凭据”更新 Access Token；“重置本地状态”清理本地错误和冷却；三者均不同于使用重置卡。
- “查看重置卡”查询可用张数、发放时间和可消费截止时间，不消耗卡。“使用 1 张重置卡”先确认，再执行一次上游兑换。兑换成功但额度快照未同步时会单独提示，请勿重复兑换。
- 订阅查询失败会保留上次已知信息并展示错误；上游不支持查询时明确显示不支持，不推断永久有效。
- “查看近 30 天用量”读取后端记录的请求与 Token 统计，和上游套餐剩余额度不同。

第一轮裁剪以入口、启动任务、控制器与前端为边界。部分共享代码、数据库字段和历史测试仍保留，因此这不是一次完整的数据库或所有适配器源码删除。

## 请求日志查看

请求日志默认查询最近 24 小时，每页 20 条，默认“按请求合并”，也可切换“逐次尝试”。支持预设或自定义时间、关键词、成功/错误/具体状态码，以及账号 ID、模型、渠道密钥 ID、错误类型、入口、流式、WebSocket 和失败后重试计划筛选。填写条件后点击“查询”；“仅看错误”可快速切换。筛选和分页在数据库执行，翻页保持同一时间范围；“刷新”重新查询，预设时间范围随当前时间更新。

合并视图使用 `GET /api/admin/usage/requests`，先按请求关联、再做服务端分页。一行显示最后保留结果、已记录尝试与重试次数、涉及账号数、累计 Token 和已观测耗时。时间、账号、模型、关键词等条件匹配任一尝试，随后找回同一请求的全部保留记录；状态按最后保留记录筛选，因此先失败后成功的请求不会被统计成最后失败。最后记录仍计划重试时显示“待后续记录”。旧记录没有关联 ID 时保持独立，没有尝试序号时次数显示未知。合并统计不依赖当前页，也不会将各次耗时直接相加冒充总耗时。

列表中的错误只显示单行摘要。鼠标悬停显示完整正文，点击固定卡片，手机可点击查看；可复制错误、打开完整请求详情，点击关闭、外部区域或按 Esc 收起。完整详情包含上下游请求 ID、账号、模型、Token、耗时、传输、内部原因及原始日志字段。

错误悬浮卡片与请求详情增加中文分类、含义和处理建议，覆盖鉴权、额度、限流、首字超时、排队/取连超时、连接失败、访问拒绝及流执行失败。根据错误文本推断的类别会保留信号说明，未知错误不强行归因；原文始终保留。

499 表示客户端取消，598 表示响应流执行未成功完成。“全部状态”与“仅错误”均包含取消记录。未记录的耗时或 Token 显示“—”。时间按浏览器本地时区显示；查询结果仍受日志保留策略和运行设置中的日志模式影响。

## 请求链路

在请求日志中点击请求 ID、“链路”，或详情中的“查看请求链路”，可按同一网关请求 ID 查看全部保留的执行记录。每个节点展示尝试序号、账号名称与 ID、状态、传输、模型、日志记录时间、耗时、首字延迟；展开查看上游请求 ID、代理、入口、Token 和内部原因。错误正文继续使用悬浮卡片。面板支持复制请求 ID 和刷新，适配手机。

- 顺序相邻的尝试区分“同账号重试”与“换号重试”。次数按有尝试序号的已保存记录计算，重复序号去重；没有序号的内部或旧执行记录单独展示，不计入重试次数。
- `is_retry_attempt` 标记的是该条失败记录之后计划继续重试，不证明后续尝试已经执行。列表和筛选已改为“计划重试”；链路面板根据后续实际记录计算已确认重试。
- 链路接口 `GET /api/admin/usage/logs/:id/chain` 需要管理密钥，以日志 ID 精确定位关联请求，不继承列表的时间、账号、状态或分页条件，最多返回最早 500 条并明确提示截断。内部子请求拥有独立请求 ID 时不并入父请求的重试次数，父 ID 作为执行字段展示。
- 开启“完整日志（full）”才能保存成功和失败记录。“仅错误”可能看不到最后成功，关闭日志、清理历史、缺失序号均可能造成链路不完整。旧记录没有关联 ID 时只展示本条，不能将无 ID 的请求合并。
- 日志异步落库，正在执行和刚完成的请求可能尚无后续记录，点击“刷新链路”重新读取。“最后记录”只代表已落库的最后一条，不保证请求已结束。链路展示本服务内已经落库的执行记录与事件快照，不能还原 New API 在外层发起的新请求重试。

### 链路事件与分段耗时

新请求采集接收、选号、账号排队、使用账号、上游执行、HTTP/uTLS 取连、WS 取连、发送、响应首字节、首个有效内容、执行结束/失败、重试决定与重试等待事件。有效内容使用严格内容判定，不把限额通知等进度事件当作内容。实际路径未经过某个采集点时显示“未采集”；事件明细默认折叠。

事件仅包含固定事件名、账号 ID、相对时间与阶段时长，不记录凭据、请求正文或代理 URL。每条执行日志保存请求截至该落库点的事件快照，最多 128 条，达到上限明确提示。选号包含账号排队，其他阶段也可能嵌套，不能直接相加；连接可能复用，取连耗时不等同于每次都新建握手。页面的“已观测总耗时”止于该执行记录，不包含记录之后的清理或未落库等待；最后一次失败后的重试等待若没有后续落库记录，不能还原。

升级会自动为 SQLite/PostgreSQL 的 `usage_logs` 增加 `execution_trace` 文本列，写入使用现有日志批量事务和保留策略，不单独逐事件写数据库。旧日志的阶段时间无法补算，显示明确提示。完整链路仍需开启 `full` 日志模式。

### 账号可用性

账号列表展示主要阻塞条件；“额度与有效期”顶部列出所有已知条件、中文原因、处理建议和预计下次检查时间。禁用、锁定、账号冷却、阈值暂停、凭据异常、并发占满和模型冷却分别解释。模型冷却只影响相应模型；多个限制必须分别解除。冷却倒计时不保证到期后可用，也不会因 Access Token 时间或额度百分数自行推断整个账号不可用；实际选号仍受模型、渠道、会话与实时调度约束。

## 请求接口

以下入口需要渠道 API Key：

| 接口 | 用途 |
| --- | --- |
| `POST /v1/responses` | Responses 执行 |
| `GET /v1/responses` | 下游 WebSocket 升级 |
| `POST /v1/responses/compact` | 上下文压缩 |
| `POST /v1/responses/input_tokens` | 输入 Token 计数 |
| `POST /v1/chat/completions` | Chat Completions 兼容 |
| `POST /v1/messages` | Messages 兼容，实际使用 Codex 池 |
| `POST /v1/messages/count_tokens` | Messages Token 计数 |
| `GET /v1/models` | 模型列表 |

无 `/v1` 前缀的对应兼容入口也保留。`/backend-api/codex` 下保留 Responses、WebSocket、compact 和模型清单。服务健康检查使用 `/health`；管理接口使用独立的 `X-Admin-Key`。

## New API 接入

1. 打开 `/admin/`，完成首次初始化或使用管理密钥登录。
2. 导入 Codex 账号，配置代理、指纹与单账号并发，检查账号状态及配额。
3. 在“渠道密钥”中创建供 New API 使用的 API Key。
4. 在 New API 中配置可发送 OpenAI Responses/Chat Completions 请求的渠道，填写此服务地址及渠道 Key。服务地址示例为 `http://<服务主机>:8080`；最终请求路径应为 `/v1/responses` 或 `/v1/chat/completions`，避免重复添加 `/v1`。
5. New API 与此服务位于 Docker 中时，使用它们共有网络中的服务名和容器端口；各容器的 `127.0.0.1` 指向自身。

New API 的终端用户密钥与此服务的渠道密钥属于不同鉴权层。不要把管理密钥用作渠道密钥。

两层重试需要共同设置次数和时间预算。后端换号受现有执行安全边界约束；已经输出语义内容后的失败不能通过盲目重放补救。通过 New API 的真实请求仍需验证会话头/元数据转发与多轮上下文连续性。

## 本地验证

需要项目指定的 Go 1.26.9 和 Node/npm 环境。

```sh
cd frontend
npm ci
npm test
npm run typecheck
npm run build
npm run test:browser
cd ..
go test ./...
```

浏览器测试使用 Playwright 和本机 Chrome，启动 `127.0.0.1:4177` 和 `127.0.0.1:4178` 测试服务器并模拟管理 API；验证登录、分页搜索、指纹配置、SSE 导入、设置增量更新、页面导航、手机布局和密钥过期，以及请求日志的服务端筛选参数、分页、长错误悬浮/点击、复制和详情，以及链路中的同账号重试、换号、计划与实际尝试区分、缺失记录提示。CI 先通过 Playwright 安装 Chrome，再运行同一浏览器测试。它不验证真实上游凭据或推理。

Go 测试覆盖服务入口/设置边界、Codex 池过滤、凭据约束，以及已有连接、调度、指纹和上下文回归。测试使用的本地监听必须被运行环境允许。

当前改造已通过上述本地测试与构建。尚未部署，也未通过 New API 发起真实推理；上线前需要单独完成真实链路联调。
